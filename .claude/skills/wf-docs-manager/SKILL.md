# Documentation Manager (Internal Engine)

An internal skill responsible for documentation file operations in `.claude-workflow/docs/`. Users do not invoke it directly — the `wf-init`, `standards-update`, and `standards-discover` skills call it.

## Core Principles

- **Project documentation is source of truth** — docs bundled with the plugin serve only as baseline/reference
- **INDEX.md is the master map** — it is always kept current after changes
- **CLAUDE.md integration is mandatory** — this is what makes the AI read the documentation

## Documentation Structure

```
.claude-workflow/docs/
├── INDEX.md                      # Master index - READ THIS FIRST
├── project/                      # Project-level documentation (generated by wf-init, not copied from templates)
│   ├── vision.md                # Project vision and goals
│   ├── roadmap.md               # Development roadmap
│   ├── tech-stack.md            # Technology choices and rationale
│   └── architecture.md          # System architecture (optional)
└── standards/                    # Technical standards and conventions
    ├── global/                  # Language-agnostic standards
    │   ├── error-handling.md
    │   ├── validation.md
    │   ├── conventions.md
    │   ├── coding-style.md
    │   ├── commenting.md
    │   └── minimal-implementation.md
    ├── backend/                 # Backend-specific standards
    │   ├── api.md
    │   ├── models.md
    │   ├── queries.md
    │   └── migrations.md
    └── testing/                 # Testing standards
        └── test-writing.md
```

## Standard File Conventions

Standard files are laid out as `standards/[category]/[topic].md`:
- **Category** = the domain folder (global, backend, testing, or a custom one)
- **Topic file** = holds several related standards

**Format**: Every file has `## Topic` as its file heading and `### Standard Name` for each individual standard. A standard gets a description of 1-10 lines (code snippets not counted) plus an optional short code example (under 10 lines).

**Conciseness**: Standards are conventions for quick reference, not tutorials. When a file becomes unwieldy, break it into focused sub-topic files.

**Why ### per standard**: Treating each standard as its own section lets agents find, update, and reference it individually — there is no bullet list to parse.

## Bundled Resources

The plugin ships the following resources with this skill:

- **Standards Directory**: Holds baseline technical standards grouped by category:
  - `global/` - Global standards (error handling, validation, conventions, etc.)
  - `backend/` - Backend-specific standards (API design, database, queries, etc.)
  - `testing/` - Testing standards (test writing, coverage, etc.)
- **INDEX.md Template**: `references/index-md-template.md` — the structure template for generating the project's INDEX.md (no static INDEX.md is shipped)

## Location Reference

- **Plugin bundles** (read-only baseline): the `docs/` subdirectory of this skill inside the plugin
- **Project documentation** (source of truth): `.claude-workflow/docs/` at the project root
- **Project configuration**: `CLAUDE.md` at the project root

## Capabilities

### 1. Initialize Documentation in Project

Run this when a project has no `.claude-workflow/docs/` yet or needs documentation for the first time. It is a **one-time baseline setup** that gives the project somewhere to start.

**IMPORTANT**: The operation takes an optional `standards_selection` parameter (an array of standard categories) that controls which standards get initialized. When it is absent, every standard is copied (backward compatible). It also takes an optional `standards_source_path` parameter for copying standards from an external project rather than the bundled defaults.

**What to do:**
1. Check whether `.claude-workflow/docs/` exists at the project root
2. If it does, warn the user that initialization will overwrite the existing documentation and ask them to confirm
3. Build the directory structure according to standards_selection:
   ```
   .claude-workflow/docs/
   ├── project/
   └── standards/
       ├── global/      (if 'global' in standards_selection or no selection provided)
       ├── backend/     (if 'backend' in standards_selection or no selection provided)
       └── testing/     (if 'testing' in standards_selection or no selection provided)
   ```
4. Copy standards into the project's `.claude-workflow/docs/standards/` directory. **Source selection**: When `standards_source_path` is given, copy from that external path. Otherwise, copy from the bundled `docs/standards/` directory of this skill:
   - **Project documentation**: Do NOT copy project templates — just create the `project/` directory. The calling skill (e.g., wf-init) generates the project documentation files (vision, roadmap, tech-stack, architecture) from analyzer data; they are not copied in as placeholder templates.
   - **Standards**: Copy only the standard categories chosen through the standards_selection parameter:
     - If `standards_selection` is empty or not provided: Copy ALL standards (backward compatible)
     - If `standards_selection` is provided: Copy only the listed categories
     - Examples:
       - `['global', 'backend', 'testing']` → Copy all three baseline categories
       - `['global', 'testing']` → Skip backend standards
5. Generate INDEX.md with entries for every piece of copied documentation (see the "Manage INDEX.md" operation):
   - For standard categories that were skipped, add placeholder sections reading "Not initialized - run standards discovery if needed"
   - Example: When backend standards are skipped, INDEX.md shows:
     ```markdown
     ### Backend Standards

     *Not initialized for this project. If you need backend standards, you can:*
     - *Add them manually using the docs-manager skill*
     - *Run `/wf-standards-discover --scope=backend` to auto-discover*
     ```
6. **MANDATORY - Update CLAUDE.md:**
   - Check whether `CLAUDE.md` exists at the project root; if it doesn't, ask the user whether to create it
   - Add the documentation reference section (see the "Manage CLAUDE.md Integration" operation)
   - Make sure it stresses reading INDEX.md at the start of any task
7. Tell the caller what documentation structure was created

**Parameters:**
- `standards_selection` (optional, array of strings): Standard categories to initialize
  - An array of category names (e.g., `['global', 'backend', 'testing']`). The baseline categories are global, backend, testing. Custom categories are supported as well.
  - If omitted or empty: Initialize every baseline standard (backward compatible)
  - If provided: Initialize only the listed categories (directories are created for custom ones)
- `standards_source_path` (optional, string): Absolute path to an external standards directory (e.g., `/path/to/other-project/.claude-workflow/docs/standards/`)
  - If provided: Copy standards from this path rather than the bundled defaults
  - If omitted: Copy from the bundled `docs/standards/` directory of this skill (default behavior)

**Result:** The project ends up with baseline documentation in `.claude-workflow/docs/`, a comprehensive INDEX.md, and CLAUDE.md integration that keeps AI assistance documentation-aware. Only the selected standard categories are initialized.

**Important:** Once this initial setup is done, the project's documentation becomes the source of truth. Teams should tailor it to their particular needs.

**Note on Skipped Standards**: When standard categories are skipped at initialization, teams can add them later through:
- The "Add Documentation File" operation, to add particular standards
- The `/wf-standards-discover` command, to auto-discover standards from the codebase

### 2. Manage INDEX.md

Run this to create or update INDEX.md, the master map of the documentation.

**What to do:**
1. Scan the directory structure of `.claude-workflow/docs/`
2. For every documentation file found:
   - Read its content to pull out a description
   - Work out the file's purpose and category
   - **For technical standards**: The description MUST list the specific practices/conventions the file documents, not merely give a generic category description.
3. Read `references/index-md-template.md` to get the INDEX.md structure template
4. Generate INDEX.md by filling the template with the discovered files and their descriptions
5. Write the generated INDEX.md to `.claude-workflow/docs/INDEX.md`
6. Confirm that CLAUDE.md references this index (see the "Manage CLAUDE.md Integration" operation)

**Result:** An up-to-date, comprehensive INDEX.md giving a clear map of all project documentation.

---

### 3. Add Documentation File

Run this to add new documentation to the project, either custom or taken from the plugin baseline.

**What to do:**
1. Decide what type of documentation is being added:
   - Project documentation (vision, roadmap, tech-stack, architecture, custom)
   - Technical standard (any category under standards/)
2. When adding from the plugin baseline:
   - Check whether the requested documentation exists in the bundled `docs/` directory of this skill
   - Copy it to the right location in `.claude-workflow/docs/`
3. When creating custom documentation:
   - Ask for the category (project/ or standards/category/)
   - Ask for the filename and its purpose
   - Create a template file with suitable frontmatter and structure
4. Update INDEX.md so it includes the new documentation (see the "Manage INDEX.md" operation)
5. If this is a technical standard that corresponds to a Claude Code Skill, make sure the two are consistent

**Result:** The new documentation is added to the project and indexed in INDEX.md.

---

### 4. Update Documentation

Run this to help the user update or change existing project documentation.

**What to do:**
1. Take the documentation identifier from the user (e.g., "project/vision", "standards/global/error-handling")
2. Check whether the documentation exists in `.claude-workflow/docs/`
3. If it exists:
   - Read the current documentation
   - Ask the user what they would like to change or update
   - Help them edit the documentation file directly
   - If they ask, optionally show them the plugin's baseline version for reference
4. If it doesn't exist:
   - Offer to add it from the plugin baseline (see the "Add Documentation File" operation)
   - Or offer to help them write custom documentation from scratch
5. Once updated:
   - Check whether INDEX.md needs an update (if the purpose/description changed significantly)
   - When tech-stack.md or architecture.md was updated, suggest reviewing CLAUDE.md for consistency
6. For technical standards:
   - If a matching Claude Code Skill exists, suggest reviewing it for consistency
   - Standards should line up with the actual code patterns in the project

**Result:** The documentation reflects the current project state and the team's decisions.

---

### 5. Use Plugin Documentation as Reference

Run this when a team wants to look at the plugin's baseline documentation for reference, or to reset particular docs to the plugin defaults.

**What to do:**
1. Compare the documentation in the bundled `docs/` directory of this skill with the project's `.claude-workflow/docs/` directory to find differences
2. Show the user which documents differ and in what way
3. Explain that the plugin documentation is baseline/reference only, and that project documentation takes precedence
4. **WARNING**: Copying plugin documentation into the project will overwrite any project-specific customizations
5. Ask the user whether they want to:
   - View the differences purely for reference (no changes)
   - Reset particular documentation to the plugin baseline (selective overwrite)
   - Reset all documentation to the plugin baseline (full overwrite - rarely recommended)
6. If the user decides to copy any documentation:
   - Copy the chosen files from the bundled `docs/` directory of this skill to the project's `.claude-workflow/docs/` directory
   - Update INDEX.md to reflect the changes
   - Review CLAUDE.md for any updates that are needed

**Important:** Use this operation rarely, mostly when a team wants to go back to the baseline. Project documentation is the source of truth and is for the team to maintain.

**Result:** The user can consult the plugin baseline documentation and, if desired, reset particular docs to the plugin versions.

---

### 6. List Available Documentation

Run this to show which documentation ships with this plugin and whether each piece is installed in the project.

**What to do:**
1. List every document in the bundled `docs/` directory of this skill, grouped by category
2. For each bundled document:
   - Show its category and name
   - Check whether it exists in the project at `.claude-workflow/docs/[category]/[name].md`
   - Show the installation status (bundled only, installed, or customized)
   - If it is installed, show whether it differs from the baseline (customized)
3. Show whether INDEX.md exists and is current
4. Show whether CLAUDE.md has documentation integration
5. Remind the user that plugin documentation is baseline/reference only, and that project documentation (when installed) is the source of truth

**Result:** The user gets a full inventory of the available baseline documentation along with its installation status in the current project.

---

### 7. Manage CLAUDE.md Integration

Run this to make sure the project's CLAUDE.md is properly wired into the documentation system, prompting the AI to read and use the documentation.

**What to do:**
1. Check whether `CLAUDE.md` exists at the project root
2. If it doesn't, ask the user whether they want it created
3. Look in CLAUDE.md for a documentation reference section
4. If that section is missing or incomplete:
   - Read `references/claude-md-template.md` to get the template
   - Add the template section to CLAUDE.md
5. Make sure the documentation section sits prominently in CLAUDE.md (close to the top)
6. Confirm that the INDEX.md path is correct and that the file exists
7. If `.claude-workflow/docs/` doesn't exist, suggest running the initialization operation first

**Result:** CLAUDE.md is properly integrated with the documentation system, so AI assistance stays documentation-aware and follows the team's conventions.

---

### 8. Validate Documentation Consistency

Run this to check that the documentation is consistent, current, and properly integrated.

**What to do:**
1. **Check structure:**
   - Confirm the `.claude-workflow/docs/` directory exists
   - Confirm every expected subdirectory exists (project/, standards/global/, etc.)
2. **Check INDEX.md:**
   - Confirm it exists and can be read
   - Check that every file in `.claude-workflow/docs/` appears in INDEX.md
   - Check that every file listed in INDEX.md really exists
   - Report any orphaned files or broken references
3. **Check CLAUDE.md integration:**
   - Confirm CLAUDE.md exists
   - Confirm it has a documentation reference section
   - Confirm it uses the valid file reference format: @.claude-workflow/docs/INDEX.md (with @ prefix, without backticks)
   - Warn when incorrect formats are used, such as `.claude-workflow/docs/INDEX.md` or `@.claude-workflow/docs/INDEX.md` (backticks)
4. **Check project documentation:**
   - Confirm the critical files exist (vision.md, tech-stack.md)
   - Check whether they hold placeholder text or real project information
   - Warn when critical documentation is missing or empty
5. **Check standards consistency:**
   - If Claude Code Skills exist, check whether matching standards documentation exists
   - If standards exist with no skills, suggest creating skills (where appropriate)
   - Report any inconsistencies
6. **Generate validation report:**
   - Summary of the documentation status
   - List of the issues found
   - Recommendations for fixing them
7. **Offer to fix issues:**
   - Ask whether the user wants the found issues fixed automatically
   - Fix missing INDEX.md entries
   - Fix missing CLAUDE.md integration
   - Create any missing directory structure

**Result:** A comprehensive validation report, with optional automatic fixes for common issues.

## Usage Examples

**Initialize documentation in a new project:**
```
User: "Set up documentation for this project"
Claude: [Executes Initialize Documentation - creates structure, copies baseline docs, generates INDEX.md, updates CLAUDE.md, gathers project info]
```

**Update project vision:**
```
User: "I want to update our project vision to include AI-first approach"
Claude: [Executes Update Documentation - reads current vision.md, helps user edit it, updates INDEX.md if needed]
```

**Add custom documentation:**
```
User: "Add documentation for our deployment process"
Claude: [Executes Add Documentation File - creates custom project/deployment.md, updates INDEX.md]
```

**Reference plugin baseline:**
```
User: "Show me the plugin's baseline error handling standard"
Claude: [Executes Use Plugin Documentation as Reference - shows plugin baseline, compares with project version, no changes unless user requests]
```

**Validate documentation:**
```
User: "Check if our documentation is complete and consistent"
Claude: [Executes Validate Documentation Consistency - checks structure, INDEX.md, CLAUDE.md integration, generates report]
```

**Manage INDEX.md:**
```
User: "Rebuild the documentation index"
Claude: [Executes Manage INDEX.md - scans .claude-workflow/docs/, regenerates comprehensive INDEX.md]
```

## Important Notes

- **Project documentation is source of truth** — docs bundled with the plugin are baseline/reference only
- **INDEX.md must stay current** — regenerate it after every documentation change
- **CLAUDE.md integration is mandatory** — it makes the AI read the documentation when a task starts
- **This skill is an internal engine** — wf-init, standards-update, and standards-discover call it. Users do not invoke it directly.
- **CRITICAL: Return control after completion** — This is an internal sub-skill. Once the requested operation is done, hand control back to the calling workflow. Do NOT treat finishing this skill as the end of the conversation turn — the parent skill still has steps to run.
